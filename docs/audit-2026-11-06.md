# Portfolio site: audit findings and fixes

Audited 6 November 2026. **Version 2.** The first version of this note contained
an error, which is corrected below. Read that section first.

Source: `github.com/bkyma10/bmyk-folio`, Astro with Tailwind, deployed
statically. Every number below was measured either in the browser on the live
site, in the built CSS, or on the actual files in the repository.

---

## Correction to version 1

**Version 1 said two images were almost the entire page weight, at roughly
2.1 MB. That is wrong. Withdraw it.**

I measured by requesting the image URLs directly. What a browser actually loads
is a different thing, because the site uses `<picture>` with a WebP source. The
browser picks the WebP every time.

Measured properly, using the resource timing API on the live homepage:

| | |
| --- | --- |
| Images requested | 10 |
| Total transferred | **527 KB** |
| Format | WebP, every one |
| The only PNG loaded | `favicon.png`, 1 KB |
| HTML | 12 KB |

The heaviest single file is `playasiaxp-1920.webp` at 156 KB, which is a
full-width cover at 1512px on a 2x display. **The image pipeline on this site is
good.** `src/components/ui/Picture.astro` emits a WebP source first, then a
fallback source, then an `<img>`. Nothing here needs rebuilding.

The lesson, and it applies to the rest of this note: measure what the browser
loads, not what the file weighs on disk.

**Version 3 adds a second withdrawal.** Version 2 claimed six images render with
no `alt` attribute. That is also wrong, and for a related reason: `alt=""` is a
valid attribute meaning "decorative", it serialises into the HTML as a bare
`alt`, and my check read it as missing. Nothing to fix there. Item 7 below is
rewritten.

## What is already working. Do not change it.

Worth stating plainly, because several of these look like faults to an
automated checker.

- **`Picture.astro`** is a proper responsive image component: WebP source,
  typed fallback source, and an `<img>` with width, height, `decoding="async"`
  and a `loading` prop. 14 components use it.
- **The header's `mix-blend-mode: difference`** inverts the logo against
  whatever is behind it. Contrast checkers report white text on white. It is
  legible, and the media query below 991px correctly switches to a solid
  header with `mix-blend-mode: normal`.
- **The logo's split letters.** The wordmark is animated chunks, so a reader
  would get "B RENDAN M A BRENDAN MA". This is handled: `Logo.astro:10` sets
  `aria-label`, and line 12 marks the wordmark `aria-hidden="true"`.
- **The header alignment.** Logo, location line and `h1` all sit at exactly
  113px on a 1512px viewport.
- **The testimonials' horizontal overflow** is a carousel. Intended.
- **`prefers-reduced-motion`** is handled properly across the logo animation,
  the section blur and the custom cursor.
- **The skip link** works.
- **`tokens.css`** is a real token system. Most fixes below are one line.

## Priority 1

### 1. Two colour tokens fail contrast, and one is used 18 times

`src/styles/tokens.css`

```
--color-grey-60: #828283;         -> 3.61:1 on --color-bg, needs 4.5:1
--color-brand-tertiary: #93887c;  -> 3.27:1 on --color-bg
```

`grey-60` is used 18 times on the rendered homepage. Change:

```
--color-grey-60: #717172;         -> 4.59:1 on #f8f8f8, 4.60:1 on white
--color-brand-tertiary: #7a7065;  -> 4.56:1 on #f8f8f8
```

Both keep the original hue and are darkened only until they pass, so nothing
about the design changes.

While in that file, the ramp has the same fault throughout. The tokens are
named by lightness percentage, which says nothing about whether a colour can
hold text:

| Token | On `--color-bg` | Usable for |
| --- | --- | --- |
| `--color-grey-80` `#4d4e50` | 7.84:1 | body text |
| `--color-grey-60` `#828283` | 3.61:1 | **fails** body text |
| `--color-grey-40` `#9fa0a3` | 2.46:1 | **fails badly** |
| `--color-grey-20` `#cfd1d7` | 1.44:1 | borders, fills |
| `--color-grey-15` `#ecedf1` | 1.10:1 | fills |
| `--color-grey-8` `#f8f9fa` | 1.01:1 | fills |

Add a comment marking grey-60 and below as fills, borders and large text only.

Also check `--color-accent-orange: #ff3d00`, at 3.55:1 on white. Fine as a fill,
not as text. If it is ever used for text, `#de3500` gives 4.55:1.

### 2. The focus ring vanishes on dark surfaces

`src/styles/global.css:47`

```css
:focus-visible { outline: 2px solid var(--color-brand); outline-offset: 3px; }
```

`#354038` is 10.81:1 on white and perfectly visible. On the near-black sections
it measures **1.69:1**, and on the pure black footer **1.94:1**. Non-text
elements need 3:1, so keyboard focus is effectively invisible there.

The site already has `is-dark-page` on `html`/`body`, so add:

```css
html.is-dark-page :focus-visible,
body.is-dark-page :focus-visible,
.site-footer :focus-visible { outline-color: var(--color-brand-secondary); }
```

`--color-brand-secondary` `#c0e1e3` on `#141517` measures 13.16:1, and it is
already a token. One rule covers both the dark pages and the footer.

Verify: tab through the footer and confirm you can see where you are.

## Priority 2

### 3. The PNG fallbacks are about 25 MB heavier than they need to be

A repository and deploy problem, not a visitor problem. No modern browser ever
requests these files, because the WebP source wins. But they are committed, they
are in git history, and they are what a browser without WebP support would get.

```
public/**/*-960.png    93 files    29.2 MB
public/**/*-960.jpg    43 files     4.3 MB   <- same job, already working
public/**/*-1280.png    7 files     5.3 MB
```

`src/data/site.ts:129` and `:131` build the fallback as
`${base}-960.${fallbackExt}` and `${base}-1280.${fallbackExt}`. `fallbackExt`
is a field that already accepts `'jpg'`. Several entries pass `'png'` where
their siblings pass `'jpg'`: `sophiaverse` and `corecover` are already JPEG,
`playasia-scene` is PNG.

Measured conversions, run here with ffmpeg at JPEG quality 4:

| File | Now | As JPEG |
| --- | --- | --- |
| `about/playasia-scene-960.png` | 819 KB | **150 KB** |
| `work/coredao-1280.png` | 1,002 KB | **110 KB** |
| `work/sail-1280.png` | 1,095 KB | **73 KB** |
| `work/coredao-960.png` | 588 KB | **74 KB** |
| `stories/.../photo-tall-960.png` | 2,234 KB | **103 KB** |

**Fix:** re-encode the PNG fallbacks as JPEG and flip `fallbackExt` for those
entries. Expect roughly 34 MB down to 5 MB. Nothing a visitor loads changes,
because they were already getting WebP.

Better long term: move the source images into `src/assets/` and let
`astro:assets` generate both formats at build time, so nothing needs to be
committed pre-sized at all.

### 4. Social previews are broken

`src/layouts/BaseLayout.astro:30`

```html
<meta property="og:image" content="/images/portrait-1600.jpg" />
```

Open Graph requires an **absolute** URL. As written, link previews on LinkedIn,
Slack and X have no image. `og:url` is already absolute, which is why this is
worth fixing rather than a mystery.

```html
<meta property="og:image" content="https://www.bmyk.design/images/portrait-1600.jpg" />
<meta name="twitter:card" content="summary_large_image" />
```

There is no `twitter:card` at all. Verify at `opengraph.xyz`.

### 5. The résumé still loads from Webflow's CDN

`src/data/site.ts:9-10`

```
resumeUrl: 'https://cdn.prod.website-files.com/66fe0de054207bcf50920737/...brendanma-resume2026.pdf'
```

If the Webflow subscription lapses, the most important link on the page for a
recruiter dies. It is one constant, used at `About/Experience.astro:26`. Move
the PDF into `public/` and point the constant at it.

### 6. Body text is sized in viewport units

`src/styles/global.css:32-33`

```css
/* Live site: font-size: 1vw — all em spacing resolves from this */
font-size: 1vw;
```

The comment shows this came across from the Webflow build, which is why it is
here. Two consequences: body text is **15.12px at a 1512px window** and grows on
a wider monitor, and a reader who sets a larger default font size gets no
change, because `vw` is not connected to their preference.

Minimum disturbance fix, keeping the fluid behaviour:

```css
font-size: clamp(1rem, 0.62rem + 0.6vw, 1.25rem);
```

Related and lower priority: the page mixes `vw`-derived `em`, `rem` and raw `px`
(18, 16, 15, 14, 20, 24, 32). Computed sizes in the browser include 15.12,
16.632, 17.01, 18.144, 19.656, 20.79 and 22.68px. Nothing lands on a scale. A
single pass converting to `rem` would make the ramp readable.

### 7. Two unused alt strings in the data. Nothing else. (rewritten in v3)

**Withdrawn as a bug.** Every image on the page has an `alt` attribute. Six of
them carry `alt=""`, which is correct here:

- The four **client logos** sit in a `<figure>` with a `<figcaption>` naming the
  company. An image plus a visible caption is the standard case for empty alt,
  and a screen reader is better off not hearing the name twice.
- The two **small about frames** in `Intro.astro` are decorative layout
  elements. `alt=""` is right. The larger `corecover` image in the same block
  does get a real description, which is the correct distinction.

The one thing worth tidying: `site.ts` defines `aboutIntro.playasia.alt` and
`aboutIntro.sophiaverse.alt`, and `Intro.astro` passes `alt=""` for both, so
those two strings are never used. Either wire them up or delete them, so the
next person does not have to work out which was intended.

## Priority 3

- **No structured data.** Zero `schema.org` blocks. A `Person` block with
  `name`, `jobTitle`, `url`, `sameAs` (LinkedIn, Instagram) and `knowsAbout` is
  a single script tag in `BaseLayout.astro`, and it helps search results.
- **`will-change: transform` is never released.** `Logo.astro:65` and `:85`. It
  should apply only while the intro animation runs, otherwise the compositor
  layer stays alive for the life of the page.
- **`Logo.astro:10`** has ``aria-label={`${site.name} — home`}``, which uses an
  em dash. Worth rewording.
- **The meta description** in `src/data/site.ts` runs about 320 characters.
  Google shows about 155, so most of it is never seen.
- **`--space-page-x`** drops to `12px` below 479px. 16 to 20 is more
  comfortable on a phone.

## Do not "fix" these

Read this before changing anything. Each looks like a bug to a checker and is
not.

1. **White logo text on white.** `mix-blend-mode: difference` on
   `.site-header` inverts it. Legible, and correctly disabled below 991px.
2. **The split-letter logo reading "B RENDAN M A".** Handled by `aria-label`
   plus `aria-hidden`. Correct.
3. **Empty sections in a full-page screenshot.** `[data-section-blur]` starts at
   `filter: blur(6px)` and sharpens on scroll. `prefers-reduced-motion` already
   removes it. One improvement worth making: if the JavaScript never runs, those
   sections stay blurred and unreadable, so add a `<noscript>` style setting
   `filter: none`.
4. **Horizontal overflow in the testimonials.** A carousel.
5. **The header alignment.** Measured, it is aligned.

## How to check the work

Measure the **rendered** page. Contrast and weight computed from the palette, or
from the files on disk, are both wrong, and wrong in both directions.

- **Contrast:** DevTools, inspect the element, use the colour picker's contrast
  readout.
- **What a browser loads:** DevTools, Network tab, or
  `performance.getEntriesByType('resource')` in the console. This is the
  measurement that caught the error in version 1.
- **Focus:** tab through the whole page, especially the footer and the dark
  sections.
- **Social cards:** `opengraph.xyz`.
- **Zoom:** set 200% and confirm nothing clips or overlaps.

## What this audit did not cover
